# Product Requirements Specification (PRS)

**Document Status:** Proposed Requirements Baseline  
**Last Reviewed:** 2026-10-16  
**Scope:** Functional (`FR-001`–`FR-028`) and Non-Functional (`NFR-001`–`NFR-016`) requirements for Radium Download Manager.  
**Related Documents:** [PROJECT_BRIEF.md](PROJECT_BRIEF.md), [FEATURE_MATRIX.md](FEATURE_MATRIX.md), [TEST_MATRIX.md](TEST_MATRIX.md)

---

## 1. Prioritization Definitions

- **Must:** Mandatory for the Minimum Viable Product (MVP, Milestones 1–3). Every `Must` requirement includes deterministic acceptance criteria.
- **Should:** High-value capability targeted for Milestone 3 or Milestone 4 once core stability is verified.
- **Could:** Desirable enhancement if schedule and complexity budgets permit.
- **Future:** Planned for post-MVP releases (Milestone 5 or later).

## 2. Functional Requirements

### 2.1 Ordinary File Downloading (`FR-001` to `FR-007`)

| ID | Priority | Requirement Statement | Acceptance Criteria (Required for `Must`) |
| :--- | :--- | :--- | :--- |
| **FR-001** | **Must** | **HTTP/HTTPS Probe & Metadata Resolution:** Given a target URL and optional request headers (`Referer`, `User-Agent`, `Cookie`), the engine shall perform an initial probe (`HEAD` with fallback to `GET` with `Range: bytes=0-0`), follow up to 10 HTTP redirects (`301`, `302`, `303`, `307`, `308`), and resolve the final URL, `Content-Length`, `Accept-Ranges` capability, `ETag` / `Last-Modified` validators, and sanitized target filename. | 1. Probe correctly identifies byte-range support when server returns `206 Partial Content` or `Accept-Ranges: bytes`.<br>2. When `HEAD` returns `405 Method Not Allowed` or `403`, engine falls back to ranged `GET` without failing.<br>3. Filename is extracted from `Content-Disposition` (RFC 5987 UTF-8 `filename*` preferred over `filename`) or URL path, and sanitized per `NFR-006`. |
| **FR-002** | **Must** | **Single-Stream Fallback for Non-Range Servers:** When a server responds with `200 OK` to a ranged request, omits `Content-Length` (chunked transfer), or sets `Accept-Ranges: none`, the engine shall download the file using a single connection and mark the task as `pause_supported = false` in the UI. | 1. Downloading a 100 MB file from a server that ignores `Range` headers succeeds via 1 stream with identical SHA-256 to source.<br>2. UI Pause button displays a clear warning that pausing will require restarting from byte 0. |
| **FR-003** | **Must** | **Dynamic Connection Spawning & Work-Stealing Byte-Range Reuse:** For range-capable transfers exceeding the minimum segment threshold (default `1 MiB`), the engine shall start with 1 connection, dynamically spawn additional connections up to `max_connections_per_task` (default `8`, max `32`), and whenever a connection finishes its assigned byte range, immediately split the largest remaining segment (`>= 2 MiB` remaining) so the idle worker assists until completion. | 1. On a 256 MiB test file over a simulated 100 Mbps link, connection count scales from 1 to 8 dynamically.<br>2. When an early segment completes while another segment has `> 2 MiB` left, the finished worker steals the second half of the remaining range without creating gaps or overlapping bytes.<br>3. Final assembled file SHA-256 matches the server file 100% of the time. |
| **FR-004** | **Must** | **Stall Detection & Automatic Connection Reset:** If any active byte-range worker receives 0 bytes for longer than `stall_timeout_sec` (default `15s`) while other workers or the network remain active, the engine shall abort that worker's HTTP request and reconnect at its last persisted `current_offset`. | 1. When a deterministic test server stalls 1 of 8 connections mid-stream for 16 seconds, the engine resets that connection at its exact byte offset and completes the download with valid SHA-256. |
| **FR-005** | **Must** | **Pause, Crash-Safe Resume, and Validator Verification:** Users shall be able to pause and resume range-capable tasks across application restarts. On resume, the engine shall send `If-Match` (if strong `ETag` present) or verify `Content-Length`/`Last-Modified` to detect server-side file replacement. | 1. Killing `openidm.exe` (`TerminateProcess`) at 50% of a 512 MiB download and restarting resumes from within `1 MiB` of the prior progress and produces a valid SHA-256 match.<br>2. If the server file changed (`ETag` mismatch or `412 Precondition Failed`), the task transitions to `Error (ValidatorMismatch)` and prompts the user before overwriting partial data. |
| **FR-006** | **Must** | **Expired URL Refresh ("Refresh Download Address"):** When a paused download fails to resume due to an expired signed URL (`401`, `403`, or `410`), the user shall be able to supply a refreshed URL (manually or captured from the browser extension) for the same file size/validator and resume from existing byte offsets. | 1. Resuming a paused task whose initial token URL returns `403 Forbidden` by supplying a new token URL for the identical file resumes from the existing partial file and completes with a valid SHA-256. |
| **FR-007** | **Should** | **Optional Post-Download Checksum Verification:** Users shall be able to paste an expected `SHA-256`, `SHA-1`, or `MD5` hash in the Task Properties dialog for automatic background verification after download completion. | — |

### 2.2 Browser Capture & Integration (`FR-008` to `FR-013`)

| ID | Priority | Requirement Statement | Acceptance Criteria (Required for `Must`) |
| :--- | :--- | :--- | :--- |
| **FR-008** | **Must** | **Automatic Browser Download Interception:** The browser extension shall intercept standard browser downloads matching user-configured file extensions (default: archives, installers, ISOs, documents, audio/video) and minimum size (default `>= 1 MiB`), cancel the built-in browser download, and forward the URL, `Referer`, `User-Agent`, and `Cookie` headers to `openidm.exe`. | 1. Clicking a 50 MiB `.zip` link in Chrome/Edge cancels Chrome's native download shelf item within 500 ms and opens the OpenIDM "Add Download" confirmation dialog with pre-populated filename, size, and headers.<br>2. If `openidm.exe` is unreachable or declines capture, the extension falls back cleanly to the browser's native download manager without losing the download. |
| **FR-009** | **Must** | **Bypass Key & Per-Site Exclusion List:** Users shall be able to bypass OpenIDM interception for a single click by holding `Alt` (or toggling the extension popup switch) and configure a domain allowlist/blocklist where automatic capture and overlays are disabled. | 1. Adding `internal.example.com` to the exclusion list prevents both file capture and DOM `<video>` overlay injection on that domain. |
| **FR-010** | **Must** | **Context-Menu "Download with OpenIDM" & Batch Text Selection Capture:** The extension shall provide browser context-menu items for single links ("Download link with OpenIDM") and selected page regions ("Download all selected links with OpenIDM"). | 1. Selecting a HTML block containing 15 `.pdf` and `.mp4` links and invoking "Download all selected links with OpenIDM" opens the OpenIDM Batch Add dialog listing all 15 resolved URLs with extension filtering. |
| **FR-011** | **Must** | **Clipboard URL Monitoring / Global Hotkey:** `openidm.exe` shall support an optional clipboard monitor for copied downloadable URLs and a configurable global hotkey (default `Ctrl+Alt+N`) to open the "Add Download" dialog pre-filled with the clipboard URL. | 1. Pressing `Ctrl+Alt+N` with a valid `https://` URL on the clipboard brings the "Add Download" dialog to the foreground with the URL pre-filled. |
| **FR-012** | **Should** | **Conflict Prevention with Other Extensions:** The extension shall detect if another extension has already canceled or claimed a `chrome.downloads` item and avoid duplicate task creation. | — |
| **FR-013** | **Could** | **UserScript / External API Bridge:** Support receiving structured media descriptors from trusted user scripts via an extension message handshake (similar to Cat Catch's `postMessage` bridge, gated by per-tab user confirmation). | — |

### 2.3 Web Media Detection (`FR-014` to `FR-018`)

| ID | Priority | Requirement Statement | Acceptance Criteria (Required for `Must`) |
| :--- | :--- | :--- | :--- |
| **FR-014** | **Must** | **Passive Network Sniffing for Progressive & Streaming Media:** The extension service worker shall monitor network responses (`webRequest.onBeforeSendHeaders` and `onHeadersReceived`) to detect progressive media (`video/*`, `audio/*` above size threshold) and adaptive streaming manifests (`.m3u8`, `.mpd`, `.ism`, `application/vnd.apple.mpegurl`, `application/x-mpegurl`, `application/dash+xml`), associating each with its `tabId`, `frameId`, page title, and request headers. | 1. Navigating to a page playing an HLS `.m3u8` or DASH `.mpd` stream records the manifest URL and its exact `Referer`, `Origin`, and `User-Agent` headers in the tab's detected media list within 1 second of the network request.<br>2. Media segments (`.ts`, `.m4s`) and tracking beacons below threshold are filtered out so only master/media manifests or full progressive files are surfaced to the user. |
| **FR-015** | **Must** | **Non-Intrusive In-Page Video Download Overlay Button:** A content script using an isolated `closed` Shadow DOM shall detect visible `<video>` elements (`>= 240x135` CSS pixels) on the page (including inside iframes), anchor a compact floating "Download Video" button near the top-right corner of the player on hover, and list all detected streams/qualities for that tab when clicked. | 1. Hovering over a `<video>` element on a test page displays the Shadow DOM button without modifying host page styles or throwing CSP errors.<br>2. Fullscreen transitions and dynamic DOM removals reposition or hide the overlay cleanly within 1 animation frame. |
| **FR-016** | **Must** | **Manifest & Variant Deduplication:** When a player fetches both a Master HLS playlist (`master.m3u8`) and subsequently fetches child media playlists (`1080p/index.m3u8`), the media detector shall group or prioritize the Master playlist so the user can choose among all available resolutions and audio tracks in a single task. | 1. Given a page that loads `master.m3u8` followed by `720p.m3u8` and `audio.m3u8`, the extension marks `master.m3u8` as the primary candidate and groups the child playlists under it in the popup/overlay menu. |
| **FR-017** | **Should** | **Opt-In Page-Context ("Deep Search") Hook:** Provide a per-site opt-in script injection (`world: "MAIN"`) that hooks `fetch`, `XMLHttpRequest`, and `MediaSource` to capture manifest URLs or one-time manifest texts when servers disguise manifest MIME types as `text/plain` or `application/octet-stream`. | — |
| **FR-018** | **Future** | **Live Stream Discovery & Recording Trigger:** Identify live HLS/DASH manifests (`#EXT-X-ENDLIST` absent or `MPD@type="dynamic"`) in the extension UI and expose a "Record Live Stream" action. | — |

### 2.4 Stream Downloading Pipeline (`FR-019` to `FR-022`)

| ID | Priority | Requirement Statement | Acceptance Criteria (Required for `Must`) |
| :--- | :--- | :--- | :--- |
| **FR-019** | **Must** | **Out-of-Process Manifest Probing & Track Selection UI:** When a user selects a detected `.m3u8`, `.mpd`, or `.ism` stream, `openidm.exe` shall invoke `N_m3u8DL-RE.exe` in probe mode (`--skip-download --write-meta-json`), parse the generated `meta.json`, and present a native Win32 Track Selection dialog allowing selection of video resolution/codec/framerate, audio language/bitrate, subtitle tracks (`.srt`/`.vtt`), and output container (`.mp4` or `.mkv`). | 1. Probing a multi-variant HLS or DASH manifest populates the Win32 Track Selection dialog with accurate resolution, codec, bandwidth, and language metadata within 3 seconds on a local test server.<br>2. DRM-protected manifests (`SAMPLE-AES-CTR` or `cenc` without user key) are flagged immediately as `Unsupported (DRM Protected)` and cannot be queued. |
| **FR-020** | **Must** | **Concurrent Stream Segment Downloading & Muxing:** Upon user confirmation, `openidm.exe` shall execute `N_m3u8DL-RE.exe` inside a Windows Job Object with the selected track filters (`-sv`, `-sa`, `-ss`), concurrent download flag (`-mt`), explicit `ffmpeg.exe` path (`--ffmpeg-binary-path`), and post-download muxing (`-M format=mp4:muxer=ffmpeg`), parsing stdout/stderr progress into the task UI. | 1. Downloading a 60-second VOD HLS stream with separate video (1080p), audio (AAC), and subtitle (WebVTT) tracks produces a single valid `.mp4` or `.mkv` file playable in Windows Media Player / VLC with synchronized audio and soft subtitles.<br>2. Temporary segment directories (`--tmp-dir`) are automatically cleaned up after successful muxing. |
| **FR-021** | **Must** | **Safe Credential Passing & Job Object Termination:** Sensitive headers (`Cookie`, `Authorization`, `Referer`) for stream tasks shall be passed via a user-ACL-restricted temporary response/cookie file rather than command-line strings, and canceling a stream task or closing `openidm.exe` shall deterministically terminate both `N_m3u8DL-RE.exe` and any child `ffmpeg.exe` processes. | 1. Inspecting `N_m3u8DL-RE.exe` command-line arguments via Process Explorer / `Win32_Process` during an authenticated stream download reveals zero `Cookie` or `Authorization` values.<br>2. Clicking Cancel or terminating `openidm.exe` leaves zero orphaned `N_m3u8DL-RE.exe` or `ffmpeg.exe` processes within 1 second. |
| **FR-022** | **Should** | **Standard HLS AES-128 Decryption Support:** Support standard HLS `#EXT-X-KEY:METHOD=AES-128` streams where the 16-byte key URI is accessible using the captured session headers/cookies or explicitly supplied by the user in advanced task options. | — |

### 2.5 Task Control, Queues, Scheduling & Preferences (`FR-023` to `FR-028`)

| ID | Priority | Requirement Statement | Acceptance Criteria (Required for `Must`) |
| :--- | :--- | :--- | :--- |
| **FR-023** | **Must** | **Task Lifecycle & Hierarchical Category Routing:** The main UI and core controller shall organize downloads by status (`All`, `Downloading`, `Paused`, `Completed`, `Failed`) and automatic category (`Video`, `Audio`, `Compressed`, `Documents`, `Programs`, `General`). Save directory resolution shall follow a strict precedence hierarchy: (1) Explicit user-specified destination, (2) Site rule domain directory/category override, (3) Custom extension mapping, (4) Configured category folder, (5) Category subfolder under default directory, (6) Global default download directory. | 1. Adding a URL matching a configured site rule or custom extension routes to the respective category and folder.<br>2. Users can pause, resume, cancel, retry, set per-task speed limits, add alternate mirror URLs, open file/folder, and delete tasks. |
| **FR-024** | **Must** | **Queue Concurrency, Global & Per-Task Speed Limiter:** Users shall be able to configure the maximum number of simultaneous active tasks in the Main Queue and apply both global and per-task bandwidth limits. Rate limiting is enforced through dual token-bucket limiters without busy-waiting loops, allowing tasks to run with specific throttles while respecting aggregate network caps. | 1. Setting a per-task speed limit caps individual worker throughput without busy-waiting CPU cycles.<br>2. Global rate limiter aggregates across all active tasks; dual limiter checks both buckets and computes sleep duration from the bottleneck bucket. |
| **FR-025** | **Must** | **Scheduled Start/Stop Windows, Auto-Retries & Post-Queue Actions:** Support task-specific and queue-wide scheduled start and stop times, configurable auto-retry with exponential backoff on transient network errors, and safe post-queue completion actions (Sleep via `SetSystemPowerState` or Shutdown via `InitiateSystemShutdownExW`). Once triggered, the completion action resets immediately to `NONE` to prevent unintended recurring actions. An explicit user pause takes precedence over schedule changes, queue schedule ticks, automatic retries, and restart recovery; only an explicit Resume action may clear it. | 1. Active downloads reaching their scheduled stop time pause cleanly without data loss.<br>2. Queue completion with action `SLEEP` or `SHUTDOWN` executes standard Windows power API calls and resets setting to `NONE`.<br>3. A user-paused task remains paused after schedule edits, repeated scheduler ticks, retry deadlines, and application restart; Resume or Resume All is required to restart it. |
| **FR-026** | **Must** | **Atomic File Replacement & Conflict Resolution:** All in-progress downloads shall write to `<filename>.openidm.part` (or a dedicated per-task temp folder for streams). Only after all bytes are verified shall the file be atomically renamed to the final destination, applying the user's conflict policy (`Auto-Rename (1)`, `Prompt`, or `Overwrite`). | 1. A failed or canceled download never leaves a truncated file with the final target extension (`.zip`, `.mp4`) in the destination folder.<br>2. Downloading `setup.exe` twice with `Auto-Rename` produces `setup.exe` and `setup (1).exe`. |
| **FR-027** | **Must** | **Windows Installer, Native Messaging Registration & Clean Uninstaller:** The installer shall deploy `openidm.exe`, `openidm-nmh.exe`, and bundled tools (`N_m3u8DL-RE.exe`, `ffmpeg.exe`), register Native Messaging manifests for Chrome, Edge, Brave, and Firefox, and provide a clean uninstaller with an option to preserve or purge `%LOCALAPPDATA%\OpenIDM`. | 1. Running the installer on a clean Windows 11 x64 VM registers the Native Messaging registry keys under `HKCU` and allows the browser extension to connect immediately without a system reboot.<br>2. Running the uninstaller removes all binaries, Start Menu shortcuts, and Native Messaging registry keys cleanly. |
| **FR-028** | **Should** | **Signed Update Checker:** Provide an opt-in update check that verifies an Ed25519-signed release manifest over HTTPS and verifies the downloaded installer's SHA-256 and Authenticode signature before execution. | — |
| **FR-038** | **Must** | **GitHub-Only Production Readiness & Clean Runner Smoke Testing:** The repository shall automate all compilation, regression suites, packaging, clean-machine installation, browser extension runtime Playwright testing, and guarded release publishing exclusively on GitHub-hosted `windows-2022` runners, eliminating developer workstation dependencies for official releases. | 1. Workflow builds x64 targets and runs C++ unit tests, extension detection, E2E integration, and performance benchmarks.<br>2. On an isolated fresh runner, generated setup installer is tested silently, verifying all binaries, manifests, registry, real loopback download with SHA256 match, auto-resume, and safe uninstallation.<br>3. Automated Playwright Chromium suite tests real extension with local fixtures.<br>4. Release publication job is strictly blocked until build, clean install, and browser tests pass. |

## 3. Non-Functional Requirements (`NFR-001` to `NFR-016`)

| ID | Category | Priority | Requirement Statement & Measurable Target (Provisional Budgets Until Benchmarked) |
| :--- | :--- | :--- | :--- |
| **NFR-001** | **Footprint** | **Must** | **Core Binary Size:** The compiled `openidm.exe` + `openidm-nmh.exe` binaries (excluding optional/bundled `ffmpeg.exe` and `N_m3u8DL-RE.exe`) shall not exceed **3.0 MB** uncompressed on Windows x64. |
| **NFR-002** | **Performance** | **Must** | **Cold & Warm Startup Time:** `openidm.exe` cold launch to interactive main window shall complete in **`< 100 ms`** on a standard Windows 11 x64 SSD system; restoring the window from the system tray shall complete in **`< 20 ms`**. |
| **NFR-003** | **Memory** | **Must** | **Idle & Active Memory Budget:** Private working set of `openidm.exe` shall remain **`< 15 MB`** when idle in the system tray with 1,000 history items, and **`< 65 MB`** during 3 concurrent 8-segment HTTP downloads at 1 Gbps. |
| **NFR-004** | **Throughput** | **Must** | **Network Saturation & CPU Overhead:** The HTTP download engine shall sustain **`>= 950 Mbps`** (line rate on 1 Gbps Ethernet) on local loopback/LAN benchmarks while consuming **`< 10%` CPU** on a 4-core x64 processor. |
| **NFR-005** | **Reliability** | **Must** | **Crash-Safe State Persistence:** Task state and segment byte offsets shall be persisted in SQLite (`WAL` mode) such that an unexpected process kill (`TerminateProcess`) or power loss loses at most **1 second or 4 MiB** of uncommitted segment progress per worker and never corrupts `state.db`. |
| **NFR-006** | **Security** | **Must** | **Strict Path & Filename Sanitization:** Every untrusted filename (`Content-Disposition`, URL path, manifest title) must be sanitized against directory traversal (`..`), drive-letter injection, NTFS Alternate Data Streams (`:`), reserved DOS names, and length overflow (`> 200` UTF-8 bytes base name), verified by unit fuzzing. |
| **NFR-007** | **Security** | **Must** | **Zero Unauthenticated Network Listeners:** Neither `openidm.exe` nor `openidm-nmh.exe` shall bind a listening TCP/UDP socket on `0.0.0.0` or `127.0.0.1` in default operation (`N_m3u8DL-RE`'s ephemeral `127.0.0.1` concat pipe during active FFmpeg merge is scoped strictly to the worker lifetime). |
| **NFR-008** | **Security** | **Must** | **Named Pipe ACL Isolation:** The IPC Named Pipe (`\\.\pipe\OpenIDM_IPC_<UserSID>`) shall be created with an explicit Win32 Security Descriptor (`SECURITY_ATTRIBUTES`) granting read/write access **only** to the current user's logon SID (`TokenUser`) and `SYSTEM`, rejecting `Everyone`, `Anonymous`, and other local user accounts, plus `FILE_FLAG_FIRST_PIPE_INSTANCE`. |
| **NFR-009** | **Privacy** | **Must** | **Credential Encryption & Log Redaction:** Transient `Cookie` and `Authorization` headers stored for paused tasks must be encrypted via Windows DPAPI (`CryptProtectData`), wiped upon task completion, and redacted (`[REDACTED]`) in all log files. |
| **NFR-010** | **Privacy** | **Must** | **Zero Telemetry by Default:** The application and browser extension shall make zero background network connections other than user-initiated downloads and opt-in update checks. |
| **NFR-011** | **Usability** | **Must** | **High-DPI, Accessibility & Dialog Consistency:** `openidm.exe` shall declare `PerMonitorV2` DPI awareness in its application manifest, scale all fonts/icons/controls cleanly across 100%–300% DPI monitors without blurriness, support full keyboard navigation (`Tab`, `Space`, `Enter`, `Delete`, `F6`), expose standard Win32 MSAA/UI Automation roles for screen readers, and use the shared charcoal surfaces and Radium coral accent (`#FF4757`) across New Download, Add Torrent, and Remove Download dialogs. |
| **NFR-012** | **Localization** | **Should** | **Externalized UI Strings & UTF-8 Path Support:** All UI strings in `openidm.exe` and the browser extension (`_locales/`) shall be externalized for localization (English `en-US` baseline, Simplified Chinese `zh-CN` and RTL layout readiness), and all file operations shall support full Unicode (`wchar_t` / UTF-16LE) paths including CJK and emoji characters. |
| **NFR-013** | **Compatibility** | **Must** | **Cross-Browser Extension Compatibility:** The browser extension shall build from a shared TypeScript codebase into a Chromium Manifest V3 bundle (Chrome, Edge, Brave) and a Firefox Manifest V3 bundle (`background.scripts` / event page + `webRequest`). |
| **NFR-014** | **Maintainability** | **Must** | **Engine Interface Decoupling:** Both the in-process HTTP engine (`IFileDownloadEngine`) and the stream worker adapter (`IStreamDownloadEngine`) shall implement pure C++ abstract interfaces so engines can be unit-tested with mock transports or swapped without modifying UI or IPC code. |
| **NFR-015** | **Compliance** | **Must** | **Strict DRM Non-Circumvention:** The system shall reject DRM-encrypted streams (`SAMPLE-AES-CTR`, Widevine, PlayReady, FairPlay) and never bundle or invoke unauthorized key-extraction tools. |
| **NFR-016** | **Portability** | **Future** | **Windows ARM64 Readiness:** All C++20 source code shall avoid x86/x64 inline assembly or architecture-specific intrinsics so `openidm.exe` and `openidm-nmh.exe` compile cleanly for `ARM64` under MSVC. |

### Extension follow-up acceptance note (2026-10-23)

Media popup results are scoped to the current document identity per tab, including History API and fragment navigation. The floating download control is placed above and aligned to a suitable video player. These behaviors require both deterministic tests and browser verification; code-level tests alone do not establish live Brave behavior.

### New Download form spacing regression (2026-10-23)

The native dialog uses shared DPI-scaled field-row metrics and retains minimum separation between each label, its control, and the following label. Coverage spans 96 through 384 DPI; actual monitor-specific visual checks remain required.

### Task removal filesystem consistency (2026-10-24)

Remove from List removes the task and its task-owned partial data while preserving completed output files. Permanently Delete removes the actual output path; for multi-file torrents it deletes only selected payload files at their metadata-relative paths. Delete, Delete File, and Shift+Delete open a compact chooser with Remove from List, Permanently Delete, and Cancel actions. Toolbar and context-menu Remove from List remain direct list-removal actions. Cancel makes no changes. If partial cleanup, output deletion, or SQLite row deletion fails, Radium reports the failure and retains the task in the in-memory list.

### Multi-file torrent entry paths (2026-10-24)

Opening or dragging a local `.torrent` file, and accepting a browser offer whose URL or suggested filename ends in `.torrent`, must open the dedicated Add Torrent dialog instead of the generic New Download dialog. Remote metainfo is fetched using the offer's request headers, then parsed before the selector appears. A multi-file torrent must display file selection before transfer; cancel removes the queued offer, while Add applies the chosen files, category, destination, and start setting to that same task.

During a BitTorrent transfer, the task's live progress must include received blocks from pieces still undergoing hash verification. Only verified pieces count as resumable data after pause, failure, or restart.
